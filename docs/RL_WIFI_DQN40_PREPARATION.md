## 固定预算

1. 一次 5/30/5 无学习短验收。
2. 最多两次 5/180/5 训练，共 72 个五秒动作周期。每次前六段 P/E/中间/P/E/中间，
   让 U/B 都覆盖三动作；随后 epsilon 从0.5按60次训练选择线性降至0.05。
3. 训练后冻结。P/E/中间/应用通知规则/DQN 各两次 5/60/5，共十个测试窗口。
   两个测试区组分别 B/U/U/B 与 U/B/B/U，各态30秒，区组内所有方法使用相同脚本。
   顺序为 P/DQN/中间/规则/E，第二组反向。DQN 首个五秒固定 P 冷启动，其成本计入测试。

总计13次计划运行、纯业务1120秒。现场2700秒封顶，至少预留180秒恢复；不能在余额不足
时开下一轮。每次采集门禁失败先保留并恢复，确认资源释放才重试一次；再次失败即停。
连续三个完整五秒队列按时率低于90%时停止更新，下一次预定边界回退P，本窗口余下时间
留在P完成采集并保留成本，随后结束整个训练批，不再续训练／测试。该性能止损不称采集无效。

## 奖励及最终判据

q 为本动作全部500条成熟生成消息的超时比例，本地失败、迟到、未回复都保留。
背景吞吐 b 使用相同五秒区间的 AP 接收载荷吞吐，单位 Mbps。奖励固定为：

```
q <= 0.05:  1 + min(b / 12, 1) - 0.02 * 是否切换
q >  0.05: -1 - 10 * (q - 0.05) - 0.02 * 是否切换
```

该奖励是本次工程选择，不保证最终达标。初始配置在预热完成，不虚构首段切换罚分。
完整五秒奖励保留切换段；没有用旧流程的稳定七秒代替全部业务。驱动的三秒保护期仅用于
辅助 HoL／概率统计，不能裁掉应用超时或背景吞吐的切换成本。

每种业务状态至少95%按时。分别在两个测试区组内，以同时达标的 P/E/中间中背景吞吐最高者
为固定基线；DQN 两个区组均达标且均有至少5%增益时，只报告值得独立复验的信号。
另报告相对应用通知规则的差异，未超过简单规则不宣称 DQN 更必要。不追加到显著。

## 离线入口

在仓库根目录，用装有 `requirements-rl.txt` 的 Python 环境运行：

```powershell
python -m unittest rl_wifi.tests.test_bounded40 -v
python -m rl_wifi.bounded40 prepare --output <全新本地方案目录>
python -m rl_wifi.bounded40 smoke --output <全新假反馈检查目录>
```

`smoke` 只验证消息／动作归属、权重更新和冻结，不是无线仿真器，输出明确标为
`offline_fixture`，实机连接和训练次数均为0。`prepare` 不导入 SSH 或 PyTorch，不收密码。
