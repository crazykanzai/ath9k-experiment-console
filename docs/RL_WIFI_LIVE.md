## 模块职责

- `rl_wifi/live_node.py`：新业务收发，复用原demo_node的硬件控制/监听/追踪/租约/恢复，不修改原文件。
- `rl_wifi/live.py`：显式小验收入口及共享场景适配，AP接收吞吐和完整应用生成分母。
- `rl_wifi/live_learning.py`：通过小验收后才允许的固定预算训练/冻结测试入口。
- `rl_wifi/analyze_live.py`：按明确命名的pilot结果与训练manifest分析，不递归纳入旧数据。

`live_learning`封存5训练窗、固定/UCB/DQN各5测试窗及随机区组顺序。均15/180/15，
15秒控制段，评分用段首3秒保护之后、段末5秒之前的7秒；整窗评估仍包含切换与探索成本。
冷启动首窗覆盖九动作；训练最多60决策段/55转移、纯业务17.5分钟，batch8/target10，
其余小网络/seed7/gamma0.9/lr0.001。测试模型冻结，固定配置只在开发数据选择；
UCB在线探索成本保留。不是ReinWiFi全部结构复现，也没有联合限速。

前景不要求饱和；背景非空≥95%、积压≥90%，仍保留Basic/24Mbps、FIFO/ABI、零probe miss、
抓包内核丢失0/接口丢失≤1%、持续时钟50ms/专项新会话首检50ms、100ms边界和恢复门禁。
ReinWiFi专属hub保存策略及(10,50]ms告警；网页共享hub首检仍10ms，正式历史规则不改。
自然重试失败、低吞吐、超时本身不是删轮理由；采集/配置/进程等门禁失败即停止，不补轮。
首轮空口接口丢3包约0.011%，未把监听配对率当MAC ACK成功率。

RTT从提交到应用确认，以发送端单调时钟测；超时从计划生成到应用确认测，包含提交前等待。
收发确认走无线，会改变AP发送行为，不能与旧纯上行实验混成同一统计总体。
应用RTT不等于成功条件MAC HoL，应用超时不等于MAC失败或碰撞。

## Python与使用边界

现有控制台`.venv`不装torch，系统Python有torch但没有paramiko。本次另建忽略目录
`tmp/rl-runtime`（继承系统torch，仅在该环境安装SSH依赖），不改原控制台依赖。
换电脑需自行创建环境并安装requirements-rl.txt和requirements-observer.txt，不复制venv。

下列仅说明接口；必须在新的当前授权及现场门禁通过后使用，不能通过循环重试绕过失败：

```powershell
# 小验收：全新输出目录；会请求内存密码
python -m rl_wifi.live --execute-live --output <new-pilot-directory>

# 通过后有界训练与对照：给定已通过pilot的result.json；全新输出目录
python -m rl_wifi.live_learning --execute-live --pilot <passing-result.json> --output <new-learning-directory>

# 已有本次材料的只读复算：全新报告目录
python -m rl_wifi.analyze_live --batch <batch-directory> --output <new-analysis-directory>
```

目前训练入口只有5窗/15窗固定预算，无自动扩展、重跑或调阈值。程序不重启、不建驱动、
不覆盖持久模块；参数恢复与授时清理由原执行器负责。遇失败应先阅读保留的manifest和回执。
程序前置检查目前只支持登记的六角色/四STA平台，不代表任意新节点/新内核已通过验收。
