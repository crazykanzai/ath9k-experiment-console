# ath9k EDCA 应用程序使用指南

本文面向需要运行 `ath9k-edca` 应用程序的用户，逐项说明当前版本已经提供的功能、命令参数、推荐执行顺序和已知限制。

> 当前项目处于实验开发阶段。驱动卸载和重载会中断 ath9k 网卡连接，并可能使网络接口暂时消失。执行相关命令前，请准备一张使用其他驱动的管理网卡或本地控制台。

## 1. 应用程序能做什么

当前应用包含以下功能：

1. 查看 Wi-Fi 接口、NetworkManager、hostapd 和 EDCA 接口状态；
2. 检查自定义 ath9k 模块是否与当前内核匹配；
3. 加载、卸载或重新加载自定义 ath9k 驱动；
4. 将指定无线接口切换为 AP 模式；
5. 将接口恢复为 NetworkManager 管理的 STA 模式；
6. 将 STA 置为明确的未连接状态 `STA_IDLE`；
7. 连接指定的 Wi-Fi 网络；
8. 查看 VO、VI、BE、BK 四个访问类别的 EDCA 参数；
9. 修改单个访问类别的 AIFS、CWmin 和 CWmax；
10. 读取对应硬件队列寄存器，检查参数是否实际写入硬件。

## 2. 当前支持环境

当前版本主要在以下环境中开发和验证：

```text
操作系统：Ubuntu 20.04
内核：5.15.0-139-generic
无线驱动：ath9k
测试网卡：Qualcomm Atheros AR9280/AR928X
应用语言：C11
```

应用依赖以下系统工具：

```text
gcc
make
modinfo / modprobe / insmod / rmmod
iw
ip
nmcli / NetworkManager
hostapd
debugfs
```

其他发行版、内核版本或 ath9k 芯片可能可以运行，但必须重新编译模块，并重新验证寄存器布局和驱动行为。

## 3. 构建应用程序

进入新项目根目录后执行：

```bash
make
make check
```

生成的应用位于：

```text
app/ath9k-edca
```

进入应用目录再运行后续命令：

```bash
cd app
```

这样默认模块目录 `./modules/<当前内核版本>` 和默认 hostapd 配置路径都会相对于 `app/` 解析。

准备默认 AP 配置：

```bash
cp config/hostapd-ath9k.conf ./hostapd-ath9k.conf
```

清理应用构建产物：

```bash
make clean
```

## 4. 准备自定义驱动模块

必须先在与运行内核严格匹配的完整 Linux 源码树中编译以下三个模块：

```text
ath9k_hw.ko
ath9k_common.ko
ath9k.ko
```

在 `app/` 目录执行：

```bash
make stage-modules \
  ATH9K_BUILD_DIR=/绝对路径/到/drivers/net/wireless/ath/ath9k
```

模块将复制到：

```text
app/modules/$(uname -r)/
```

应用在改变网络状态前，会使用 `modinfo` 检查三个模块的 `vermagic` 是否匹配当前内核。

也可以不使用默认目录，在驱动命令中显式指定：

```bash
--module-dir /绝对路径/到/modules
```

或者设置环境变量：

```bash
export ATH9K_MODULE_DIR=/绝对路径/到/modules
```

## 5. 命令基本格式

应用命令的基本格式为：

```bash
sudo ./ath9k-edca <无线接口名> <命令> [参数]
```

本文使用 `wlp1s0` 作为示例。实际使用时应替换为测试机上的 ath9k 接口名。

可以先查看系统无线接口：

```bash
iw dev
```

## 6. 查看应用和接口状态

### 6.1 `status`：查看当前 Wi-Fi 状态

```bash
sudo ./ath9k-edca wlp1s0 status
```

该命令会显示：

- 应用判断的状态：`STA_IDLE`、`STA_CONNECTED`、`AP_PARTIAL`、`AP_RUNNING` 或 `UNKNOWN`；
- 802.11 接口类型；
- 当前 SSID；
- IPv4 地址；
- 链路状态；
- NetworkManager 状态和连接名称；
- 本应用管理的 hostapd 是否运行；
- ath9k 的 `edca_ctrl` debugfs 接口是否可用。

该命令不会主动改变接口状态。

## 7. 驱动管理功能

### 7.1 `driver status`：检查驱动和模块

```bash
sudo ./ath9k-edca wlp1s0 driver status
```

指定模块目录：

```bash
sudo ./ath9k-edca wlp1s0 driver status \
  --module-dir /绝对路径/到/modules
```

该命令会显示：

- 当前内核 release；
- 使用的模块目录；
- `ath9k_hw`、`ath9k_common`、`ath9k` 是否已经加载；
- 待加载模块的 `vermagic` 是否匹配；
- 当前接口是否提供 EDCA 扩展。

即使无线接口暂时不存在，也可以执行此命令检查模块文件。

### 7.2 `driver reload`：重新加载自定义驱动

```bash
sudo ./ath9k-edca wlp1s0 driver reload
```

执行过程包括：

1. 检查三个自定义模块；
2. 停止本应用管理的 hostapd；
3. 断开 STA，并让 NetworkManager 暂时释放接口；
4. 关闭接口并清除地址；
5. 按依赖顺序卸载旧 ath9k 模块；
6. 加载自定义模块；
7. 等待接口重新出现；
8. 将接口恢复为 `STA_IDLE`。

重载成功后不会自动连接原来的 Wi-Fi。目标状态是：接口为 managed、未关联 SSID、没有本应用的 hostapd。

> 模块卸载是全局操作，不只影响命令行中填写的一个接口。当前版本的完整事务回滚仍在完善中，因此必须保留独立管理链路。

### 7.3 `driver unload`：卸载 ath9k 模块

```bash
sudo ./ath9k-edca wlp1s0 driver unload
```

成功后，ath9k 接口会消失，直到重新加载驱动。该命令适合驱动开发和恢复流程，不建议在远程连接依赖该网卡时执行。

### 7.4 `driver load`：从已卸载状态加载自定义驱动

```bash
sudo ./ath9k-edca wlp1s0 driver load
```

指定模块目录：

```bash
sudo ./ath9k-edca wlp1s0 driver load \
  --module-dir /绝对路径/到/modules
```

该命令要求三个 ath9k 模块当前均未加载。成功后的目标状态同样是 `STA_IDLE`。

## 8. AP 和 STA 模式管理

### 8.1 `mode ap`：启动 AP 模式

```bash
sudo ./ath9k-edca wlp1s0 mode ap \
  --config ./hostapd-ath9k.conf \
  --ip 192.168.50.1/24
```

应用会：

1. 读取并验证 hostapd 配置；
2. 确认配置中的 `interface` 与命令接口一致；
3. 让 NetworkManager 释放接口；
4. 清除旧 IP 地址；
5. 启动本应用管理的 hostapd 实例；
6. 等待 AP 类型和 Beacon 服务就绪；
7. 配置 AP 本机 IPv4 地址；
8. 再次验证 AP、SSID、hostapd、链路和地址。

如果省略 `--config`，默认使用：

```text
./hostapd-ath9k.conf
```

如果省略 `--ip`，交互终端会提示输入，默认值为 `192.168.50.1/24`。非交互环境必须显式传入 `--ip`。

当前示例配置是开放实验 AP，而且应用只配置 AP 本机地址，不自动提供 DHCP、DNS、NAT 或防火墙隔离。

### 8.2 `mode sta`：返回普通 STA 模式

```bash
sudo ./ath9k-edca wlp1s0 mode sta
```

该命令会：

- 停止本应用管理的 hostapd；
- 清除 AP 地址；
- 将接口类型设为 managed；
- 将接口交回 NetworkManager；
- 验证接口已经退出 AP 模式。

NetworkManager 可能自动连接已经保存的网络。如果需要明确保持未连接状态，请使用 `mode idle`。

### 8.3 `mode idle`：进入明确的 STA_IDLE

```bash
sudo ./ath9k-edca wlp1s0 mode idle
```

等价命令：

```bash
sudo ./ath9k-edca wlp1s0 sta-idle
```

应用会确保命令完成时满足：

- 接口类型为 managed；
- 当前没有关联 SSID；
- 没有本应用管理的 hostapd；
- NetworkManager 继续管理该接口。

## 9. 连接 Wi-Fi 网络

### 9.1 `sta-connect`：连接指定 STA 网络

推荐使用隐藏输入密码的方式：

```bash
sudo ./ath9k-edca wlp1s0 sta-connect \
  --ssid ExampleSSID \
  --name ExampleConnection
```

应用会在终端提示输入密码。`--name` 是可选的 NetworkManager 连接名称。

也可以显式传入密码：

```bash
sudo ./ath9k-edca wlp1s0 sta-connect \
  --ssid ExampleSSID \
  --password ExamplePassword \
  --name ExampleConnection
```

不推荐在真实环境使用 `--password`，因为密码会进入 shell 历史和进程参数。即使使用隐藏提示，当前版本最终仍需把密码交给 `nmcli`，后续版本将继续改进凭据传递方式。

连接成功的当前判断条件是：

- 接口处于 managed 模式；
- 已关联 SSID；
- NetworkManager 报告连接；
- 已取得 IPv4 地址。

如果 DHCP 获取地址较慢，当前版本可能在连接实际成功后仍报告最终验证失败，这是待改进项。

## 10. EDCA 参数查看与修改

### 10.1 `show`：查看驱动中的 EDCA 队列参数

```bash
sudo ./ath9k-edca wlp1s0 show
```

典型输出形式：

```text
AC=VO qnum=0 aifs=2 cwmin=3 cwmax=7
AC=VI qnum=1 aifs=2 cwmin=7 cwmax=15
AC=BE qnum=2 aifs=3 cwmin=15 cwmax=1023
AC=BK qnum=3 aifs=7 cwmin=15 cwmax=1023
```

`qnum` 由运行中的驱动提供，应用不会假定某个 AC 永远对应固定硬件队列。

### 10.2 `set`：修改一个 AC 的 EDCA 参数

格式：

```bash
sudo ./ath9k-edca <接口> set <VO|VI|BE|BK> <AIFS> <CWmin> <CWmax>
```

示例：

```bash
sudo ./ath9k-edca wlp1s0 set BE 4 15 63
```

当前参数约束：

- AIFS：1 到 15；
- CWmin/CWmax：只能是 `1, 3, 7, 15, 31, 63, 127, 255, 511, 1023`；
- CWmin 不能大于 CWmax；
- AC 名称为 VO、VI、BE 或 BK，不区分大小写。

驱动会保留 TXOP、readyTime 和其他未指定的队列属性。应用在写入成功后会打印软件层读回，但当前版本不会自动比较目标值和硬件寄存器值，因此建议继续执行 `hw` 检查。

### 10.3 `hw`：读取硬件寄存器参数

查看全部 AC：

```bash
sudo ./ath9k-edca wlp1s0 hw
```

只查看一个 AC：

```bash
sudo ./ath9k-edca wlp1s0 hw BE
```

应用会根据运行时 `qnum` 计算对应的 `AR_DLCL_IFS` 寄存器地址，并解析：

- AIFS；
- CWmin；
- CWmax；
- 原始寄存器值。

当前实现通过 ath9k 已有的 `regidx/regval` debugfs 接口读寄存器，多进程并发读取仍可能互相影响。实验时应避免同时运行多个实例。

### 11.1 驱动和接口准备

```bash
cd app
sudo ./ath9k-edca wlp1s0 driver status
sudo ./ath9k-edca wlp1s0 driver reload

```

### 11.2 进入目标网络模式

AP 实验：

```bash
sudo ./ath9k-edca wlp1s0 mode ap \
  --config ./hostapd-ath9k.conf \
  --ip 192.168.50.1/24
```

STA 实验：

```bash
sudo ./ath9k-edca wlp1s0 mode sta
sudo ./ath9k-edca wlp1s0 sta-connect --ssid ExampleSSID
```

### 11.3 记录默认值

```bash
sudo ./ath9k-edca wlp1s0 show
sudo ./ath9k-edca wlp1s0 hw
```

### 11.4 设置实验参数并再次读回

```bash
sudo ./ath9k-edca wlp1s0 set BE 4 15 63
sudo ./ath9k-edca wlp1s0 show
sudo ./ath9k-edca wlp1s0 hw BE
```

### 11.5 运行流量并保存数据

此部分由实验方案决定。至少应记录：

- 项目和驱动 Git commit；
- 内核、模块 `vermagic` 和 SHA-256；
- 网卡型号、PCI ID、接口和 PHY；
- AP/STA 拓扑、信道和带宽；
- EDCA 请求值、软件读回值和硬件读回值；
- 流量类型、持续时间和重复次数；
- 吞吐、时延、抖动、丢包、重传等原始结果。

> 驱动重载、接口模式切换和重新关联可能覆盖 EDCA 参数。应先稳定网络模式，再执行 `set`，并在每次实验开始前重新读回确认。

## 12. 兼容命令

当前程序保留以下旧版命令：

```bash
sudo ./ath9k-edca wlp1s0 ap-start [CONFIG] [IP]
sudo ./ath9k-edca wlp1s0 ap-stop
sudo ./ath9k-edca wlp1s0 sta-mode
sudo ./ath9k-edca wlp1s0 sta-disconnect
```

对应关系：

| 兼容命令 | 推荐的新命令 |
|---|---|
| `ap-start` | `mode ap` |
| `ap-stop` | `mode sta` |
| `sta-mode` | `mode sta` |
| `sta-disconnect` | `sta-idle` 或 `mode idle` |

新脚本和新文档应优先使用推荐命令。

## 13. 常见问题

### 13.1 提示接口不存在

先检查：

```bash
iw dev
sudo ./ath9k-edca wlp1s0 driver status
```

如果驱动已卸载，应先执行 `driver load`。

### 13.2 模块 kernel mismatch

说明 `.ko` 的 `vermagic` 与当前 `uname -r` 不匹配。必须使用当前内核对应的头文件、配置和 `Module.symvers` 重新编译，不能强制加载其他内核版本的模块。

### 13.3 EDCA extension unavailable

检查：

- 当前模块是否确实包含自定义 `edca_ctrl`；
- ath9k debugfs 是否启用；
- debugfs 是否挂载；
- 命令是否具有 root 权限；
- 接口是否确实绑定到 ath9k。

### 13.4 AP 配置接口不一致

确保 `hostapd-ath9k.conf` 中：

```text
interface=wlp1s0
```

与命令行传入的接口完全一致。

### 13.5 怎样恢复系统自带 ath9k

如果自定义模块已经卸载，可以尝试从系统模块目录重新加载：

```bash
sudo modprobe ath9k
```

如果当前处于部分加载或异常网络状态，应通过本地控制台根据 `lsmod`、`dmesg` 和系统模块路径进行恢复。当前应用的自动恢复流程仍在完善中。

## 14. 命令返回值

- 命令成功：进程返回 `0`；
- 参数错误、权限不足、状态验证失败或外部工具失败：进程返回非 `0`；
- 自动化脚本应同时检查返回值和最终状态，不应只搜索终端中的 `success` 文本。

## 15. 首轮实验细节与结果

### 15.1 实验目标

本轮实验由于硬件能力有限，仅能验证所修改的驱动是否有更改硬件的能力。

### 15.2 实验硬件与拓扑

使用由微相E200搭载openwifi作为AP，该AP运行相关上位机可以查看接收到的流量。ath9k网卡作为STA，通过GL-SFT1200中继连接到E200；另外开一个GL-SFT1200作为STA，直接连接E200，竞争信道。

### 15.3 实验步骤

- 首先根据实验硬件和拓扑情况构建网络，值得注意的是作为中继的GL-SFT1200的需要连接E200的Wi-Fi，ath9k网卡连接中继路由器。
- 其次，需要确定连接是否成功，让ath9k网卡ping 192.168.10.122，正常不需要过多操作是可以直接ping通的。如果不通需要检查路由情况，即
`ip route get 192.168.10.122`
- 直连GL-SFT1200的路由器，和ath9k网卡，分别向着E200打流，指令为：
`iperf3 -c 192.168.10.1 -p 5202 -u -b 10M -t 60 -l 1470 -f m`
其中两者打流的端口要不同，一个是5201，一个是5202

### 15.4 实验结果

实验命令的目标发送速率为 `10 Mbit/s`，目标时长为 `60 s`。根据本轮截图，结果汇总如下。表中的 CWmin 均指 ath9k 的 BE 队列参数；“GL-SFT1200 竞争流”是另一台直连 E200 的设备在对应 ath9k 参数下产生的流量。

| 被观察流 | ath9k BE CWmin | 有效时长 | 发送端汇总 | 接收端汇总 | 抖动 | 丢包 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ath9k 经中继流 | 15 | 60 s | 10.0 Mbit/s | 6.56 Mbit/s | 7.169 ms | 16025 / 49830（32%） |
| ath9k 经中继流 | 511 | 60 s | 3.51 Mbit/s | 3.49 Mbit/s | 5.778 ms | 14 / 17884（0.078%） |
| GL-SFT1200 竞争流 | 15 | 18.22 s 后中断 | 10.0 Mbit/s | 无有效汇总 | 无有效汇总 | 无有效汇总 |
| GL-SFT1200 竞争流 | 511 | 60 s | 10.0 Mbit/s | 9.96 Mbit/s | 0.145 ms | 0 / 51020（0%） |

### 15.5 结果分析与已知限制

本轮结果可以支持以下简单结论：

- `CWmin=511` 的硬件读回证明驱动接口能够修改 BE 队列参数，完成了本轮最主要的功能验证。
- ath9k 经中继流的接收速率由 6.56 Mbit/s 降至 3.49 Mbit/s，约下降 46.8%，趋势符合 CWmin 增大后信道竞争机会减少的预期。
- 不能把丢包率下降解释为链路质量提高，因为 `CWmin=511` 组的实际发送速率也降到了 3.51 Mbit/s。此外，GL-SFT1200 的 `CWmin=15` 对照提前中断，本轮又只有一次测试，因此暂时不能给出稳定性或公平性的定量结论。

#### GL-SFT1200 中继是否可靠、是否透明

GL-SFT1200 可以完成普通 IP/UDP 流量转发，因此作为临时联网和扩大覆盖范围的设备是可用的；但它不适合作为要求链路透明的 EDCA 性能测量组件。

根据 [GL.iNet 官方 Repeater 说明](https://docs.gl-inet.com/router/en/4/interface_guide/internet_repeater/)，默认 Repeater 使用 WISP 模式，会建立独立子网并充当防火墙；[官方网络模式说明](https://docs.gl-inet.com/router/en/4/interface_guide/network_mode/) 还表明路由模式会启用 NAT 和 DHCP。因此，普通 IP 数据虽然能够通过，但这不是二层透明透传，也不能保证上游保留 ath9k 终端原有的 MAC 和无线链路特征。

[GL-SFT1200 官方数据表](https://static.gl-inet.com/www/images/products/datasheet/sft1200_datasheet_20240301.pdf) 列出了 Wireless Bridge 模式。桥接模式可以避免默认 WISP 的路由隔离，更接近二层透传，但设备仍需接收并重新发送数据，会增加一跳无线竞争、排队和重传；官方也提示无线 Extender 可能使可用带宽减半。因此，GL-SFT1200 不是“只把信号放大”的透明射频放大器。

综上，这套拓扑可用于当前的驱动写入功能验证，但不足以单独证明 EDCA 算法性能。后续应优先让 ath9k 终端直接关联可控 AP，构建路径对称的竞争实验；若仍使用 GL-SFT1200，应至少记录固件版本、网络模式、上下行频段和信道，并确认 DHCP 来源及是否存在 NAT。
